# Native integration design — hand-written review tools (R2 design study)

Status: IMPLEMENTED (R3, 2026-07-29) — tool surface, factory extension,
tiers, and tests landed as specified below; e2e retarget implications for
R4 are at the end.

Context: the autogenerated 61-tool API-parity layer (`codegen/`,
`gdocs_preview/generated/`) is being deleted in a parallel chunk. This note
specifies its replacement: a small set of hand-written, ergonomic
edit-suggestion and comment tools that follow upstream
(taylorwilsdon/google_workspace_mcp) conventions closely enough to be
upstream-PR-able. All conventions below are cited against the stable upstream
code in this fork.

---

## 1. Upstream conventions (study results, with citations)

### 1.1 Tool structure & naming (gdocs/docs_tools.py)

- **Verb-first names, `doc`/`docs` noun**: `search_docs` (docs_tools.py:89),
  `create_doc` (:389), `modify_doc_text` (:455), `find_and_replace_doc`
  (:738), `inspect_doc_structure` (:1350), `manage_doc_tab` (:2588).
  Upstream mixes `doc` (content tools) and `document` (comment factory:
  `list_document_comments` / `manage_document_comment`, docs_tools.py:2778-2782,
  core/comments.py:82-83). Drive has a `check_` verb precedent:
  `check_drive_file_public_access` (core/tool_tiers.yaml:42).
- **Consolidated `manage_*` tools with an `action` string param** are the
  house pattern for multi-op surfaces: `manage_document_comment`
  (core/comments.py:104-123, dispatch at :37-66 with
  `action.lower().strip()` + `ValueError` for bad/missing combos),
  `manage_doc_tab` (docs_tools.py:2588), `manage_event`, `manage_task`
  (tool_tiers.yaml:48,137).
- **Decorator stack, outermost first**: `@server.tool(title=...,
  annotations=ToolAnnotations(...))` → `@handle_http_errors(name,
  [is_read_only=True,] service_type="docs")` → `@require_google_service(...)`
  (docs_tools.py:78-89, 444-455; curated layer identical:
  gdocs_preview/curated_tools.py:67-80).
- **Param conventions**: injected `service: Any` first, then
  `user_google_email: str`, then the file id (`document_id: str`), then
  operation params; optionals default `None` (docs_tools.py:455-478).
- **Docstring house style** (this is what the MCP client sees): summary
  line(s), optional TIP/guidance prose, `Args:` block naming every param,
  `Returns:` block with `str:` description. gdocs core tools omit types in
  Args (docs_tools.py:490-513); the curated review layer writes
  `name (type): text` (curated_tools.py:104-110). **New tools use the
  curated `name (type):` form** — it is the established style of the module
  they live in.
- **Return conventions**: gdocs content tools return human-readable
  confirmation strings with IDs and an edit link (docs_tools.py:427-441,
  721-724); the curated review layer returns
  `json.dumps(..., indent=2, ensure_ascii=False)` strings
  (curated_tools.py:114, 218, 267). **New review tools return JSON strings**
  (callers need machine-readable IDs; consistent within the service), always
  including a `link` field with the doc edit URL, mirroring the house habit
  of ending confirmations with a link.
- **Error handling**: raise `UserInputError` for validation problems — it is
  re-raised unwrapped by `handle_http_errors` (core/utils.py:35-38,
  534-537). `HttpError` is wrapped into a user-friendly `Exception` with
  re-auth hints on 401/403 (core/utils.py:538-590).
  `@handle_http_errors(..., is_read_only=True)` adds SSL retry for reads
  (core/utils.py:491-508). Precedent for catching `HttpError` *inside* a
  tool to classify preview errors before the decorator sees it:
  `docs_review_capabilities` (curated_tools.py:191-208).
- **ToolAnnotations**: read tools `readOnlyHint=True, destructiveHint=False,
  idempotentHint=True, openWorldHint=True` (docs_tools.py:80-85); creators
  `readOnlyHint=False, destructiveHint=False, idempotentHint=False`
  (:380-385); text mutators `destructiveHint=True` (:446-451).

### 1.2 Comment factory (core/comments.py)

`create_comment_tools(app_name, file_id_param)` (core/comments.py:69-217)
builds exactly two tools per app — `list_{app}_comments` and
`manage_{app}_comment` (:82-83) — via three literal per-app branches (so the
file-id param keeps its native name in the schema), registers them by
setting `__name__` and calling `server.tool(...)` (:203-212). All comment
ops go through **Drive v3** `comments`/`replies` (:252, 315, 342) with scope
group `("drive", "drive")` for writes — full Drive scope "so comment
operations remain visible to collaborators" (:101-102). Instantiation is one
line per app: docs_tools.py:2778, sheets_tools.py:2435, slides_tools.py:477.
Actions today: `create` (unanchored only — Drive API cannot anchor,
:114-117), `reply`, `resolve` (:47-66).

### 1.3 Scopes (auth/scopes.py, auth/service_decorator.py)

- Scope groups relevant here: `"docs_read"` → `documents.readonly`,
  `"docs_write"` → `documents`, `"drive"` → full Drive, `"drive_read"`,
  `"drive_file"` (service_decorator.py:535-551). `documents` implies
  `documents.readonly` in the hierarchy (scopes.py:100).
- `DOCS_PREVIEW_SCOPES` = docs read+write + Drive full/read/file
  (scopes.py:201-207), registered as service `docs_preview` in
  `TOOL_SCOPES_MAP` (:223) and `TOOL_READONLY_SCOPES_MAP` (:246).
- **Decision: no scope changes.** Every new tool rides existing groups
  (`docs_read` / `docs_write` / `drive`); `DOCS_PREVIEW_SCOPES` already
  covers the whole review deployment (incl. the Drive-based factory comment
  tools) and stays byte-identical. Zero diff in auth/.

### 1.4 Tool tiers (core/tool_tiers.yaml)

Tiers (`core` ⊂ `extended` ⊂ `complete`) only gate registration when the
server is started with a tier flag (`resolve_tools_from_tier`,
core/tool_tier_loader.py:99-118; main.py:246-259); default runs register
every tool of every enabled service. Placement is therefore about sensible
subsetting, not security. House pattern: primary workflow in `core`,
secondary in `extended`, diagnostics/debug in `complete`
(tool_tiers.yaml:56-78 — `debug_table_structure`, `inspect_doc_structure`
are `complete`).

### 1.5 Kept hand-written modules

- `gdocs_preview/analysis.py` — pure suggestion diffing (pre/post text,
  UTF-16 index discipline, context windows); **reused unchanged** by
  the list tool (analysis.py:283-366) and read tool (:387-446).
- `gdocs_preview/curated_tools.py` — 3 review tools
  (`docs_review_list_suggestions`, `docs_review_capabilities`,
  `docs_review_read_document`, curated_tools.py:35-39). Kept, renamed
  (§2). One autogen dependency must go: `_manifest_summary` reads
  `generated/manifest.json` (:46-57) — deleted with the autogen layer.
- `gdocs_preview/preview_status.py` — process-wide enrollment verdict:
  `classify_preview_error(status, message)` (preview_status.py:35-57),
  `record(availability, evidence, source)` (:60-67), `get_status()`
  (:70-75). **Reused unchanged** — `source` is a free string, new tools
  record `source="tool_call"`.

### 1.6 Preview API shapes (from codegen/overlay/docs_preview_overlay.json)

`docs/preview-api-reference.md` did not exist at study time; shapes are
cross-checked against the overlay (still on disk) and the generated
docstrings. All preview ops are `documents.batchUpdate` request-union
members (overlay `Request` schema):

- `acceptSuggestion` / `rejectSuggestion`: `{suggestionId}`. Accept needs
  edit access (403 otherwise); reject needs edit access OR suggestion
  authorship (overlay `x_overlayNotes[4]`).
- `insertComment`: `{content (≤2048 UTF-8 units, non-empty),
  assigneeEmailAddress?, range?}` where `range` =
  `{startIndex, endIndex, segmentId?, tabId?}`; unanchored behavior with
  `range` omitted is UNDOCUMENTED (`x_overlayNotes[0]`) — we always require
  a range (unanchored create already exists via the Drive factory).
  Reply lands in `replies[0].insertComment...` → `InsertCommentResponse
  {commentThread}` (member name unconfirmed — e2e records it).
- `addCommentReply`: `{post: {content}, commentId | suggestionId}` —
  exactly one of the thread-id union. Response reply:
  `AddCommentReplyResponse {post}`.
- `writeControl.writeMode = "SUGGEST"` turns any of the 32
  SUGGEST-compatible GA requests (incl. `insertText`,
  `deleteContentRange`) into suggestions (overlay `WriteControl`).
- `BatchUpdateDocumentResponse` preview fields: `suggestionResponses[]`
  (1:1 with requests; `createdSuggestionIds`, `acceptedSuggestionIds`,
  `rejectedSuggestionIds`, ...) and `commentUpdateState`
  (`ALL_SAVED` / `ALL_FAILED_UNKNOWN_REASON` / `NO_UPDATES_REQUESTED`) —
  thread ops can fail even when the batch returns 200; **must be checked**.
- Not-enrolled shape: the request field itself fails proto-parse → HTTP 400
  with "Unknown name"/"Cannot find field" markers
  (preview_status.py:19-23); other 400s mean the preview surface parsed the
  request (enrolled) and failed on semantics.
- `deleteSuggestion`, `updateCommentPost`, `deleteCommentReply`,
  `deleteComment` exist in the union but are descoped (§6) — comment
  update/delete go through GA Drive API instead.

## 2. Design decisions (the three big calls)

### D1 — Comment factory: extend for Drive-GA ops, do NOT push preview into it

Split by API surface, which is also the least-intrusive split:

- **`update` and `delete` comment actions are app-agnostic Drive v3 GA
  operations** (`comments.update`, `comments.delete` — same service, same
  `("drive", "drive")` scope, same dispatch shape as the existing
  create/reply/resolve). They are added **inside the factory** as two new
  actions on the existing `manage_{app}_comment` tools. All three apps
  (Docs/Sheets/Slides) gain them for free, no new tool names, no signature
  changes (`comment_id`/`comment_content` params already exist,
  core/comments.py:104-111). This is the change upstream would actually
  want — it fills an obvious gap in their own tool.
- **Anchored create, suggestion ops, and thread replies are Docs-API
  Developer-Preview, docs-only operations** (wrong service, wrong scope
  group, enrollment-gated, `Range`/thread concepts that don't exist for
  Sheets/Slides). Pushing them into core/comments.py would force
  preview-only branches into a file instantiated by three services.
  They live as doc-specific tools in `gdocs_preview/` (D2).

### D2 — Module placement: stay in `gdocs_preview/`

Judged purely on upstream conventions and merge-friendliness:

- The `docs_preview` service integration already exists and is exactly the
  "self-contained module + 3 integration lines" shape: `SERVICE_MODULES`
  (main.py:192), `TOOL_SCOPES_MAP` (auth/scopes.py:223), and a
  tool_tiers.yaml section. After this design, **all three lines already
  exist and none change** (only the tiers *list content* changes).
- Preview tools registered under the GA `docs` service would auto-register
  enrollment-gated tools for every upstream user — unmergeable. An opt-in
  service (`--tools docs_preview`) is the mergeable shape; upstream's own
  mechanism (main.py:178-195) exists for exactly this.
- Resulting package: `analysis.py` (pure), `preview_status.py` (state),
  `curated_tools.py` (read/diagnostic tools), **new `write_tools.py`**
  (preview write tools). One new file; no file renames (minimizes conflict
  with the concurrent autogen deletion, which touches only `generated/`,
  `codegen/`, and the two references in §4).

### D3 — Suggest-edit tool shape: one range-based tool mirroring `modify_doc_text`

`suggest_doc_edit(document_id, start_index, end_index=None, text=None, ...)`
— the SUGGEST-mode twin of `modify_doc_text` (docs_tools.py:455-478), with
its three modes derived from which params are set (insert / delete /
replace) rather than an `action` enum. Rationale: reviewers hold
`start_index`/`end_index` straight out of `list_document_suggestions` /
`get_doc_review_view` output (both emit API-verbatim UTF-16 indexes,
analysis.py:9-16), and the param names match the tool upstream users
already know. Replacement is `deleteContentRange` **then** `insertText` at
`start_index` in a single batchUpdate with `writeControl.writeMode=
"SUGGEST"` — same order as `modify_doc_text`'s replacement path
(docs_tools.py:604-617); in SUGGEST mode the deleted text remains in the
document (marked), so the insert index needs no shifting. Whether the two
requests yield one or two suggestion ids is unknown — the tool returns
**all** `createdSuggestionIds` from `suggestionResponses` and e2e records
the reality.

### D4 — Naming: rename the three curated tools to house verb-first style

The `docs_review_*` prefix is not an upstream pattern (no service prefixes
anywhere: calendar's `manage_event`, chat's `send_message`, docs'
`create_doc`). Since R4 retargets the e2e harness anyway and the
tool_tiers docs_preview section is rewritten anyway, renaming is nearly
free now and buys full house consistency:

| old (curated_tools.py:35-39) | new |
|---|---|
| `docs_review_list_suggestions` | `list_document_suggestions` |
| `docs_review_read_document` | `get_doc_review_view` |
| `docs_review_capabilities` | `check_docs_review_capabilities` |

Noun convention: suggestion/comment thread tools use `document`
(mirroring the factory pair `list_document_comments` /
`manage_document_comment`); content-edit tools use `doc` (mirroring
`modify_doc_text` / `create_doc`). `get_` / `check_` verbs follow
`get_doc_content` / `check_drive_file_public_access` precedent.

## 3. Final tool surface

7 tools in the `docs_preview` service (3 renamed + 4 new) plus 2 new
actions on the existing factory tools. One line each:

| tool | purpose |
|---|---|
| `list_document_suggestions` | List every pending suggestion with computed pre/post text, context, indexes, author (exists; renamed) |
| `get_doc_review_view` | Read the doc as a reviewer sees it: CriticMarkup markers + paragraph map (exists; renamed) |
| `check_docs_review_capabilities` | Scope/tool inventory + Developer Preview enrollment verdict, optional live probe (exists; renamed, manifest dependency removed) |
| `suggest_doc_edit` | Create a suggested insertion/deletion/replacement via `writeMode=SUGGEST` (new) |
| `manage_document_suggestion` | Accept or reject a suggestion by id (new) |
| `reply_to_doc_thread` | Reply to a comment thread OR suggestion thread (Docs preview `addCommentReply` union) (new) |
| `create_anchored_doc_comment` | Create a comment anchored to a text range via Docs preview `insertComment` (new) |
| `manage_document_comment` (+`manage_spreadsheet_comment`, `manage_presentation_comment`) | gains `update` and `delete` actions (Drive GA; factory extension) |

### 3.1 Exact specifications

All new/renamed tools live in service `docs_preview`; decorator stack,
docstring style (`name (type):`), and JSON-string returns per §1.1. Every
tool's first two real params are `user_google_email: str`, `document_id:
str` (after the injected `service: Any`).

#### `suggest_doc_edit` — NEW (write_tools.py)

```python
@server.tool(title="Suggest Doc Edit", annotations=ToolAnnotations(
    readOnlyHint=False, destructiveHint=False,  # creates a pending suggestion; nothing applied
    idempotentHint=False, openWorldHint=True))
@handle_http_errors("suggest_doc_edit", service_type="docs")
@require_google_service("docs", "docs_write")
async def suggest_doc_edit(service, user_google_email: str, document_id: str,
                           start_index: int,
                           end_index: Optional[int] = None,
                           text: Optional[str] = None,
                           tab_id: Optional[str] = None,
                           segment_id: Optional[str] = None) -> str
```
Modes (validation first, all failures = `UserInputError`):
- `text` set, `end_index` None → suggested **insertion** of `text` at
  `start_index`: `[{insertText: {location: {index, segmentId?, tabId?}, text}}]`.
- `text` None, `end_index` set → suggested **deletion** of
  `[start_index, end_index)`:
  `[{deleteContentRange: {range: {startIndex, endIndex, segmentId?, tabId?}}}]`.
- both set → suggested **replacement**: `[deleteContentRange, insertText@start_index]`
  in that order (§2 D3).
- neither set → `UserInputError("Provide text (insertion), end_index
  (deletion), or both (replacement).")`.
- `end_index is not None and end_index <= start_index` → `UserInputError`.
- `start_index < 1` → `UserInputError` telling the caller to take indexes
  from `list_document_suggestions` / `get_doc_review_view` (deliberate
  deviation from `modify_doc_text`'s index-0 aliasing, docs_tools.py:588-627:
  review flows always start from listed indexes; no silent remapping).
  `Location`/`Range` construction: include `segmentId`/`tabId` keys only
  when non-None (empty segmentId means body).

Executes via the shared preview helper (§3.2) with `write_mode="SUGGEST"`.
Returns JSON:
`{"document_id", "mode": "insertion|deletion|replacement",
"created_suggestion_ids": [...], "requests_applied": <int>, "link"}`
where ids are the union of `createdSuggestionIds` across
`suggestionResponses` (may be empty if the API omits the field — never
fabricated). Docstring must state: indexes are UTF-16 code units in the
SUGGESTIONS_INLINE coordinate space; the edit lands as a *pending
suggestion*, visible to `list_document_suggestions` and in the Docs UI.
Tier: `core`.

#### `manage_document_suggestion` — NEW (write_tools.py)

```python
@server.tool(title="Manage Document Suggestion", annotations=ToolAnnotations(
    readOnlyHint=False, destructiveHint=True,  # accept applies deletions; reject discards the suggestion
    idempotentHint=False, openWorldHint=True))
@handle_http_errors("manage_document_suggestion", service_type="docs")
@require_google_service("docs", "docs_write")
async def manage_document_suggestion(service, user_google_email: str, document_id: str,
                                     action: str, suggestion_id: str) -> str
```
`action.lower().strip()` ∈ `{"accept", "reject"}` (dispatch style of
core/comments.py:46-66; invalid → `UserInputError("Invalid action ...
Must be 'accept' or 'reject'.")`). Request:
`[{acceptSuggestion|rejectSuggestion: {suggestionId: suggestion_id}}]` via
the preview helper (no write_mode). Returns JSON: `{"document_id",
"action", "suggestion_id", "accepted_suggestion_ids" |
"rejected_suggestion_ids" (from suggestionResponses, may be empty),
"link"}`. Docstring notes the permission rules (accept: edit access;
reject: edit access or authorship — overlay `x_overlayNotes[4]`) and that
a nonexistent id may surface as a 400 error OR a 200 no-op with
`commentUpdateState` (curated_tools.py:150-153) — the helper reports
`comment_update_state` when the API sends it. Tier: `core`.

#### `reply_to_doc_thread` — NEW (write_tools.py)

```python
@server.tool(title="Reply to Doc Thread", annotations=ToolAnnotations(
    readOnlyHint=False, destructiveHint=False, idempotentHint=False, openWorldHint=True))
@handle_http_errors("reply_to_doc_thread", service_type="docs")
@require_google_service("docs", "docs_write")
async def reply_to_doc_thread(service, user_google_email: str, document_id: str,
                              reply_content: str,
                              comment_id: Optional[str] = None,
                              suggestion_id: Optional[str] = None) -> str
```
Exactly one of `comment_id` / `suggestion_id` must be set (mirrors the
API's `thread_id` union) → else `UserInputError("Provide exactly one of
comment_id or suggestion_id.")`. Empty/whitespace `reply_content` →
`UserInputError` (API requires non-empty, ≤2048 UTF-8 units — length is
NOT pre-validated; the API error is authoritative). Request:
`[{addCommentReply: {post: {content: reply_content},
commentId|suggestionId}}]` via the preview helper, which also enforces
`commentUpdateState` (§3.2). Returns JSON: `{"document_id", "thread_type":
"comment"|"suggestion", "comment_id"|"suggestion_id", "post_id"
(from the reply's AddCommentReplyResponse.post.postId when present, else
null — member name recorded by e2e), "comment_update_state", "link"}`.
Docstring: replies are authored as the authenticated user; suggestion
threads exist only after a SUGGEST-mode edit; comment-thread ids come from
`create_anchored_doc_comment` / `list_document_comments`. Tier: `core`.

#### `create_anchored_doc_comment` — NEW (write_tools.py)

```python
@server.tool(title="Create Anchored Doc Comment", annotations=ToolAnnotations(
    readOnlyHint=False, destructiveHint=False, idempotentHint=False, openWorldHint=True))
@handle_http_errors("create_anchored_doc_comment", service_type="docs")
@require_google_service("docs", "docs_write")
async def create_anchored_doc_comment(service, user_google_email: str, document_id: str,
                                      content: str, start_index: int, end_index: int,
                                      segment_id: Optional[str] = None,
                                      tab_id: Optional[str] = None,
                                      assignee_email: Optional[str] = None) -> str
```
Validation: non-empty `content` (`UserInputError`); `end_index >
start_index >= 1` (`UserInputError`). Range is REQUIRED — unanchored
create stays on `manage_document_comment(action="create")` (Drive), and
range-omitted behavior is undocumented (overlay `x_overlayNotes[0]`).
Request: `[{insertComment: {content, assigneeEmailAddress?
(from assignee_email), range: {startIndex, endIndex, segmentId?,
tabId?}}}]` via the preview helper with `commentUpdateState` enforcement.
Returns JSON: `{"document_id", "comment_id", "anchor_id", "quoted_text"
(CommentThread.plainTextQuote), "comment_update_state", "link"}` — thread
fields extracted from `replies[0]` when present, else nulls (member name
recorded by e2e). Docstring: comment appears in the Docs UI anchored to
the range exactly like a human comment; indexes are UTF-16 units per the
current document; use `list_document_comments` to enumerate afterwards.
Tier: `core`.

#### Factory extension — core/comments.py (`update`, `delete` actions)

- `_manage_comment_dispatch` (core/comments.py:37-66) gains:
  - `"update"`: requires `comment_id` and `comment_content` →
    `_update_comment_impl(service, app_name, file_id, comment_id,
    comment_content)`:
    `service.comments().update(fileId=file_id, commentId=comment_id,
    body={"content": comment_content},
    fields="id,content,author,createdTime,modifiedTime")` (Drive v3
    requires explicit `fields` on comments.update). Returns human string in
    the house shape of `_create_comment_impl` (:302-329):
    `"Comment updated successfully!\nComment ID: ...\nModified: ...\nContent: ..."`.
  - `"delete"`: requires `comment_id` → `_delete_comment_impl(service,
    app_name, file_id, comment_id)`:
    `service.comments().delete(fileId=file_id, commentId=comment_id)`
    (empty response). Returns
    `"Comment {comment_id} deleted from {app_name} {file_id}."`.
  - The invalid-action message (:64-66) becomes
    `"... Must be 'create', 'reply', 'resolve', 'update', or 'delete'."`.
- The three per-app `manage_comment` docstrings (:112-120, :151-159,
  :190-198) each gain two action lines:
  `- update: Update a comment's text. Requires comment_id and comment_content.`
  `- delete: Permanently delete a comment and its replies. Requires comment_id.`
- `MANAGE_COMMENT_ANNOTATIONS` (:29-34): `destructiveHint=False` →

### 3.2 Shared preview execution helper (write_tools.py, private)

```python
async def _execute_preview_batch_update(
    service: Any, tool_name: str, document_id: str,
    requests: list[dict], *, write_mode: Optional[str] = None,
    enforce_comment_update: bool = False) -> dict
```
Single choke point for every preview write:
1. Build body `{"requests": requests}` (+
   `{"writeControl": {"writeMode": write_mode}}` when set) and call
   `service.documents().batchUpdate(...)` via `asyncio.to_thread`
   (pattern: docs_tools.py:713-717, curated_tools.py:178-181).
2. On success: `preview_status.record("available", {"http_status": 200,
   "reason": "preview_request_succeeded"}, source="tool_call")`.
3. On `HttpError`: decode status/content exactly like the probe
   (curated_tools.py:192-196), classify via
   `preview_status.classify_preview_error` and `record(...,
   source="tool_call")`. If the verdict is `("unavailable",
   "not_enrolled")`, raise
   `UserInputError(f"{tool_name} requires Google Workspace Developer "
   f"Preview enrollment for the authenticated project. Enrollment steps: "
   f"pending_for_human.md. Verify with "
   f"check_docs_review_capabilities(probe=true).")` — surfaced verbatim to
   the client (core/utils.py:534-537). Otherwise re-raise the `HttpError`
   so `handle_http_errors` produces the standard 401/403/other messaging
   (core/utils.py:538-590).
4. If `enforce_comment_update=True` (thread ops: reply, anchored create)
   and `response.get("commentUpdateState") ==
   "ALL_FAILED_UNKNOWN_REASON"`, raise
   `Exception(f"{tool_name}: the API returned HTTP 200 but reported "
   "commentUpdateState=ALL_FAILED_UNKNOWN_REASON - the thread operation "
   "was NOT saved. Retry; if it persists, check enrollment and document "
   "permissions.")` — partial failure must never look like success
   (overlay `BatchUpdateDocumentResponse.commentUpdateState`).
5. Return the raw response dict.

Preview-gating summary (the "not-enrolled surfaces how?" answer): every
preview write tool fails with the same actionable `UserInputError` naming
`check_docs_review_capabilities`, and every call — success or failure —
feeds `preview_status`, so probe-free capability reports stay fresh.
